## 1. 背景与目标

### 1.1 背景

- 团队在**内网（隔离网络）环境**中开展 Python 项目开发与安全审计，无法在线调用 OSV.dev、NVD 等漏洞数据源。
- pip 依赖包存在已知漏洞（CVE/GHSA/PYSEC）时，上线前需要人工翻阅公告，效率低、易遗漏。
- 市面上工具（pip-audit、safety 等）均依赖运行时联网，不适用内网场景。

### 1.2 产品目标

做一个**内网离线**的 pip 依赖漏洞扫描工具：

1. 用户提交依赖清单（多行输入或 requirements.txt），工具输出：是否存在已知漏洞、漏洞详情、严重级别、**修复建议**；
2. 结果支持 **JSON**（结构化，供二次处理）与**成型报告**（HTML，供人阅读/存档）；
3. 漏洞库与程序**完全解耦**：漏洞库在外网机器上定期"爬取"生成数据文件，摆渡进内网后**只替换数据文件**即可完成升级（最小化更新，程序无需重装）。

### 1.3 成功标准

- 在完全断网的内网机器上完成扫描全流程，不发起任何网络请求；
- 已知漏洞（如 `requests==2.28.0` 的 CVE-2023-32681）能被正确检出，且不误报已修复版本；
- 漏洞库升级 = 拷入一个增量数据包 + 一条命令，全程不动程序代码；
- 一份 50 项依赖的 requirements.txt 扫描在 10 秒内出结果（普通办公机）。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 漏洞库 (VulnDB) | 从公开数据源抓取并加工后的本地漏洞数据文件，含全量库与增量包两种形态 |
| 同步器 (sync) | 运行在**外网机**上的采集程序，负责抓取、加工、生成全量库/增量包 |
| 摆渡 | 数据经由 U 盘/网闸等介质从外网传入内网的过程 |
| OSV | Google 开源漏洞库格式/服务，聚合 GitHub Advisory (GHSA)、PyPA (PYSEC)、CVE 等来源 |
| PEP 440 | Python 包版本号规范，`1.2.3rc1`、`2.0.post1` 等格式的比较规则 |

## 3. 总体方案

### 3.1 三件套架构

```
┌───────────── 外网机（可联网） ─────────────┐        ┌────────────── 内网机（隔离） ──────────────┐
│                                            │        │                                            │
│  pythonscan-sync（同步器）                  │        │  pythonscan（扫描器 CLI）                   │
│  ┌──────────┐   ┌──────────────────────┐   │  摆渡  │  ┌──────────┐   ┌───────────────────────┐  │
│  │ 数据源抓取│ → │ 全量库 pypi-adv-*.zip │ → │ ────→ │  │ db import│ → │ 本地漏洞库 (~/.pythonscan) │  │
│  │ OSV 全量  │   │ 增量包 delta-*.zip    │   │  U盘/  │  │ db update│   │ （仅数据，程序不更新）    │  │
│  └──────────┘   └──────────────────────┘   │  网闸  │  └──────────┘   └───────────────────────┘  │
│                                            │        │        ↑ 输入：多行依赖 / requirements.txt   │
└────────────────────────────────────────────┘        │        ↓ 输出：终端 / JSON / HTML 报告       │
                                                      └────────────────────────────────────────────┘
```

### 3.2 解耦原则（本次需求的核心）

| 解耦面 | 做法 |
| --- | --- |
| **程序 ↔ 漏洞库** | 漏洞库是带 `schema_version` 的标准数据文件；程序启动时读取库 manifest（版本、条目数、校验和），不匹配时报错提示而非误扫。升级漏洞库只需替换/导入新数据文件 |
| **全量 ↔ 增量** | 首次部署导入全量库；此后同步器对比上一快照，只生成**自上版以来的差异增量包**（通常仅几 KB~几 MB），满足"尽量只更新一个文件、最小化更新" |
| **扫描引擎 ↔ 界面** | 引擎（库加载、匹配、建议、报告渲染）封装为独立模块并暴露纯 Python API；v1 的 CLI 与后续的桌面 GUI 都只是引擎之上的一层壳【默认决策：先 CLI，GUI 列入 v2 规划】 |
| **数据 ↔ 来源** | 库内每条漏洞记录保留 `source` 字段（osv/ghsa/pysec/nvd…），未来新增数据源不改变库格式与扫描器逻辑 |

### 3.3 默认决策（评审重点确认项）

| # | 决策点 | 【默认决策】 | 理由 |
| --- | --- | --- | --- |
| D1 | 第一版形态 | CLI + 终端交互式多行输入（"输入框"以终端多行录入形式实现）；GUI 为 v2 | 与此前"先 CLI 后 GUI"一致，最快可用；引擎解耦后 GUI 可低成本套壳 |
| D2 | 成型报告格式 | HTML 单文件报告 + **PDF 导出**（`--pdf`，本机浏览器无头打印实现），另产出 JSON 结构化结果 | 零第三方依赖、内网友好；PDF 不引入 Python 第三方库，复用内网机自带的 Edge/Chrome |
| D3 | 漏洞库形态 | 全量库打底 + 增量包最小化更新 | 扫任意包无需反复摆渡；日常更新量极小 |
| D4 | 依赖策略 | 扫描器零第三方依赖（纯 Python 标准库，Python ≥ 3.9）；同步器允许极少数来源工具 | 内网安装第三方依赖困难；版本比较自实现 PEP 440 子集，解析失败时降级为"需人工确认"，绝不给出错误建议 |

## 4. 功能需求

### FR-1 依赖输入（三种方式，可组合互斥）

| 方式 | 说明 |
| --- | --- |
| ① 交互式多行输入 | `pythonscan scan` 直接回车进入录入模式：逐行输入 `包名==版本号`，**一行一个**，空行/`Ctrl+Z`(Win)/`Ctrl+D`(Unix) 结束 |
| ② 依赖清单文件 | `pythonscan scan -i deps.txt`，文件内容与交互式录入格式一致（一行一个） |
| ③ requirements.txt | `pythonscan scan -r requirements.txt`，直接扫描现成依赖文件 |

**输入行格式与容错规则**：

- 支持 `requests==2.28.0`、`requests@2.28.0`、`requests 2.28.0`、裸 `requests`（未指定版本）；
- 忽略：空行、`#` 注释（整行与行内）、`-r`/`-e`/`--index-url` 等 pip 选项行；
- 包名按 PEP 503 规范化（`Django`、`django`、`Django_X` 视为同一包）；extras（`requests[security]`）与环境标记（`; python_version > "3.8"`）剥离后处理；
- 非法行（无法解析出包名）**不中断扫描**：跳过并计入报告"解析告警"清单；
- **未指定版本的依赖（如只输入 `requests`）**：不视为错误，按以下策略处理：
  - 结果标注"未固定版本"，列出该包**全部已知漏洞**，按严重级别分组、每条附影响版本区间，供用户对照实际使用的版本；
  - 给出可执行的下一步指引：如何获取当前版本（`pip show <包名>` / `pip freeze`）后精确复扫；
  - 可选开关 `--use-installed`：对未给版本的条目，用标准库 `importlib.metadata` 从当前 Python 环境探测已安装版本，探测到则按该版本精确扫描并在结果中标注 `version_source=environment`；探测不到则回退到"全量列出"并标注原因。

**验收标准**：上述四种写法解析结果一致；含 3 条非法行的 10 行清单能正常扫描其余 7 行，且报告尾部可见 3 条告警；只输入 `requests`（无版本）能输出全量漏洞列表 + 固定版本指引；在装有 requests 的环境中使用 `--use-installed` 能自动探测版本并精确扫描。

### FR-2 离线漏洞匹配（核心引擎）

- 启动时加载本地漏洞库（含索引：包名 → 漏洞记录偏移），按规范化包名取候选集；
- 对每条候选的受影响区间（OSV `affected.ranges`，`introduced`/`fixed`/`last_affected` 事件模型）做**本地版本匹配**，版本比较遵循 PEP 440 子集（epoch、release 段、pre/rc、post、dev）；
- 匹配结果去重合并：同一漏洞在库内以"主 ID + 别名"存储（规则见 §5.4），同一包的输出中每条漏洞只出现一次；
- 引擎为纯函数式 API：`scan(items: list[Dependency]) -> ScanResult`，供 CLI、GUI、测试共同复用。

**验收标准**：`requests==2.28.0` 检出 CVE-2023-32681（修复于 2.31.0）；`requests==2.32.3` 按当时库内容判定（正确区分受影响与已修复版本）；`1.10rc1` 这类预发布版本可被正确比较。

### FR-3 修复建议

- **漏洞级**：每条漏洞给出 `fixed` 版本（数据源自带）；
- **包级**：给出"建议升级目标版本"= 覆盖该包当前版本全部已知漏洞的**最低版本**（即各漏洞 fixed 版本中的最大值，存在多分支时说明取舍逻辑）；
- 库中记录了 PyPI 最新版本时，额外提示"该包最新版本为 x.y.z"；建议不可靠（版本无法解析比较）时输出"需人工确认"，不硬给结论；
- **未固定版本条目**：无当前版本，不输出覆盖率类结论；建议目标 = 库内该包最新版本，并注明该最新版本是否仍存在已知漏洞（依库内数据判定）；
- 报告中修复建议与对应漏洞关联展示，便于逐条核对。

**验收标准**：`flask==0.12.2`（存在多个不同 fixed 版本的漏洞）能给出单一、正确、覆盖全部漏洞的升级目标。

### FR-4 输出（终端 / JSON / HTML）

| 输出 | 触发 | 内容 |
| --- | --- | --- |
| 终端摘要 | 默认 | 风险统计、每个受影响包的漏洞条目（ID、级别、摘要、修复版本、 advisory 链接）、告警与错误 |
| JSON | `--json out.json`（或 `-o out.json` 后缀识别） | §7 定义的结构化结果，供流水线/二次处理 |
| HTML 报告 | `-o report.html` 或 `--report` | §8 定义的成型报告，中英双语跟随 `--lang` |
| PDF 报告 | `--pdf report.pdf` | 与 HTML 同模板、同内容，经本机浏览器无头打印生成（§8.2） |

### FR-5 requirements.txt 批量扫描

- 完整支持 FR-1 方式③；结果按"依赖项"逐行列出状态（有漏洞 / 干净 / 未固定版本 / 解析失败 / 库中无记录）；
- 汇总统计：总依赖数、受影响数、漏洞按严重级别分布。

### FR-6 漏洞库管理与更新

| 命令 | 作用 |
| --- | --- |
| `pythonscan db import <全量库.zip>` | 首次部署导入全量库（覆盖旧库前校验 manifest 与校验和） |
| `pythonscan db update <增量包.zip>` | 应用增量包（新增/修改/删除漏洞条目），仅数据文件变更 |
| `pythonscan db info` | 显示当前库：schema 版本、快照日期、条目数、来源、校验和 |

- 库过期提醒：报告与终端显示库快照日期；快照距今超过 **90 天**（可配置）显示醒目警告【默认决策：90 天】；
- 增量包必须声明"基于哪个库版本"，版本不衔接时拒绝应用并提示先补全量或按序应用。

### FR-7 中英双语

- 文案层与引擎层分离（i18n 字典），CLI 参数 `--lang zh|en`，默认 `zh`；可用环境变量 `PYTHONSCAN_LANG` 设置；
- JSON 结果中的**数据字段**（漏洞摘要等）保持来源原文，不做翻译；**界面/报告框架文案**双语。

### FR-8 退出码

`0` = 无已知漏洞；`1` = 发现已知漏洞；`2` = 运行错误（库缺失/文件不存在/参数错误）。便于内网脚本批量调度时判断结果。

## 5. 漏洞库规范（数据层）

### 5.1 数据来源【默认决策】

| 来源 | 用途 | 备注 |
| --- | --- | --- |
| **OSV.dev PyPI 全量导出**（主源） | 漏洞记录本体 | 单个 zip（NDJSON，OSV 格式），天然聚合 GHSA / PYSEC / CVE 别名，覆盖 PyPI 生态，免 Key |
| PyPI JSON API（辅源） | 包是否存在、最新版本号（用于修复建议提示） | 仅同步器抓取关心的包，数据并入库 manifest 附表 |

> v1 不接 NVD 直连：OSV 已带 GHSA 的 CVSS 评分；PYSEC 部分记录无评分时显示"未评级"。NVD 增强列为 v1.1 可选（见开放问题）。

### 5.2 文件形态

```
pypi-advisories-20260913.zip      # 全量库（首次部署）
├── manifest.json                 # schema_version / 快照日期 / 条目数 / 各文件 sha256 / 生成器版本
├── advisories.jsonl              # 漏洞记录（逐行 JSON，OSV 字段子集 + 加工字段）
└── index.json                    # 包名 → 记录定位（含包级最新版本附表）

delta-20260913-to-20261001.zip    # 增量包（日常更新，只含变化）
├── manifest.json                 # base=20260913, target=20261001, 变更统计
├── upsert.jsonl                  # 新增/变更记录
└── deletions.json                # 需删除的记录 ID
```

### 5.3 库内记录字段（OSV 子集 + 加工）

`id`、`aliases`、`summary`、`details`、`severity`（级别 + CVSS 向量/评分，取来源最高分）、`affected`（包名、受影响区间事件）、`fixed_versions`（加工字段：区间解析结果）、`references`、`source`、`published/modified` 时间。

### 5.4 去重合并规则

同一漏洞多来源记录（GHSA-x、PYSEC-y、OSV-CVE 条目互为 alias）合并为一条：主 ID 优先级 `CVE-* > GHSA-* > PYSEC-*`，其余进 `aliases`；severity 取各来源最高；references 合并去重。

### 5.5 最小化更新流程（用户视角）

```
外网机:  python sync.py            → 若已有旧快照则产出 delta-*.zip（否则全量）
摆渡:    拷贝 delta-*.zip 进内网
内网机:  pythonscan db update delta-*.zip
         → 校验 base 版本衔接 + sha256 → 原子替换数据文件 → 完成（程序未动）
```

### 5.6 兼容性

- `schema_version` 采用 `v1`；扫描器兼容同大版本全部小版本；大版本升级时由新程序自带迁移命令处理；
- manifest 校验失败（文件损坏/被篡改）→ 拒绝加载并明确报错。

## 8. 成型报告（HTML / PDF）

1. **头部**：PythonScan 标识、扫描时间、依赖来源、漏洞库快照日期（含过期警告横幅）、语言版本；
2. **总览**：依赖总数 / 受影响包数 / 漏洞总数、严重级别分布（色块统计）、Top 风险包；
3. **详情区**：每个受影响包一张卡片——漏洞表（ID/别名、级别与评分、摘要、影响范围、修复版本、参考链接）、包级修复建议；
4. **干净清单**：未发现漏洞的依赖（折叠展示）；
5. **附录**：解析告警与错误、数据来源与免责说明（"仅覆盖漏洞库快照内的已知漏洞"）。

技术约束：单文件 HTML、内联 CSS、不依赖外网 CDN、可离线打印为 PDF；禁用外部 JS（内网安全考虑）。

### 8.2 PDF 导出机制【v0.3 新增】

不引入第三方 Python PDF 库，采用"HTML 模板 + 本机浏览器无头打印"方案：

- `--pdf report.pdf` 时，扫描完成、HTML 报告生成后，调用本机已安装的 Edge / Chrome 无头模式（`--headless --print-to-pdf`，标准库 `subprocess` 实现）将同一 HTML 打印为 PDF，版式与 HTML 完全一致；
- 浏览器探测顺序：环境变量 `PYTHONSCAN_BROWSER` → Edge 常见安装路径 → Chrome 常见安装路径 → PATH；
- 找不到可用浏览器：不中断流程，明确提示并降级为"保留 HTML，浏览器打开后 Ctrl+P 手动另存为 PDF"；
- HTML 模板无任何外部资源引用，保证无头打印与手动打印均为离线可用。

## 10. 边界与非目标（v1 不做）

- 不做漏洞利用判定/可达性分析（静态清单比对，非代码级分析）。
