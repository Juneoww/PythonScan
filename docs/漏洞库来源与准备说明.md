# PythonScan 漏洞库来源与准备说明

适用版本：PythonScan v0.1.0，漏洞库格式 `schema_version=1`。更新日期：2026-10-14。适用人员：负责外网数据准备、内网摆渡及漏洞库维护的开发和运维人员。

PythonScan 的漏洞数据来自 OSV 的 PyPI 生态导出。外网机器下载并加工数据，生成 PythonScan 专用全量库或增量包；内网机器只读取导入后的本地库。常规数据更新不需要重新打包或更换 EXE。

首次部署准备一份全量库。后续每次更新仍需在外网获取最新上游全量数据，保存本次生成的全量库，再选择向内网摆渡全量库或增量包。下面的流程可直接作为操作规程使用。

## 漏洞库来源

### 直接下载源

项目同步器默认下载：

```text
https://osv-vulnerabilities.storage.googleapis.com/PyPI/all.zip
```

OSV 官方文档给出的对应对象是 `gs://osv-vulnerabilities/PyPI/all.zip`，也提供以下 HTTPS 访问形式：

```text
https://storage.googleapis.com/osv-vulnerabilities/PyPI/all.zip
```

OSV 聚合不同来源的漏洞记录，并持续导出到其维护的公共存储桶。PythonScan 使用其中的 **PyPI 生态数据**，不是跨全部生态的 `all.zip`。[OSV 数据来源与导出说明](https://google.github.io/osv.dev/data/#data-dumps)

### 公告来源与编号

| 来源或编号 | 含义 | 在本项目中的关系 |
| --- | --- | --- |
| OSV | 聚合平台及漏洞数据格式 | 同步器直接下载其 PyPI 导出 |
| GitHub Advisory Database | 收集和维护开源软件安全公告，通常使用 GHSA 编号 | 经 OSV 聚合后进入候选数据 |
| Python Packaging Advisory Database | PyPA 社区维护的 Python 包漏洞公告，使用 PYSEC 编号 | 经 OSV 聚合后进入候选数据 |
| CVE | 漏洞标识，可与 GHSA、PYSEC 记录互为别名 | 本项目没有直接抓取 NVD 的实现 |
| OpenSSF Malicious Packages | 以 OSV 格式发布的恶意包报告，通常使用 MAL 编号 | PyPI 导出中可能包含此类记录，但本工具不提供完整恶意包检测能力 |

GitHub 数据库包含 CVE 和 GitHub 来源公告；PyPA 数据库面向发布在 PyPI 上的包。同一漏洞可能有多个编号，因此同步器按 ID 与别名关系合并记录。[GitHub Advisory Database](https://github.com/github/advisory-database)、[PyPA Advisory Database](https://github.com/pypa/advisory-database)、[OpenSSF Malicious Packages](https://github.com/ossf/malicious-packages)

### 最新包版本信息

可选参数 `--fetch-latest` 会访问 `https://pypi.org/pypi/<包名>/json`，读取 `info.version` 并写入库索引。它提供包版本元数据，用于展示库内记录的最新版本；同步器的漏洞记录仍取自 OSV 导出。[PyPI JSON API](https://docs.pypi.org/api/json/#get-a-project)

省略该参数仍能生成漏洞库，并扫描指定包版本。v0.1.0 预置库未包含最新版本表。

## 数据如何成为本地漏洞库

```text
外网机器
  OSV PyPI 原始 all.zip
    → sync.sync 读取 JSON 并筛选 PyPI 条目
    → 规范化包名、按别名合并、裁剪字段
    → PythonScan 全量库
    → 与上一份全量库比较后，可另生成增量包

经 U 盘或网闸等介质摆渡

内网机器
  pythonscan db import 或 db update
    → 本地 vulndb.zip
    → CLI 或 GUI 离线扫描
```

三种 ZIP 文件不能混用：

| 文件 | 用途 | 内网如何使用 |
| --- | --- | --- |
| OSV 原始 `all.zip` | 保存上游公告 JSON，作为同步器输入 | 不能直接 `db import` |
| PythonScan 全量库 | `kind=full`，包含完整本地索引及包记录 | `db import`，也可由 GUI 直接选择 |
| PythonScan 增量包 | `kind=delta`，包含包级变更、删除及基准信息 | 只能对衔接的本地全量库执行 `db update` |

全量库结构为：

```text
manifest.json        schema_version、kind、snapshot、记录数及文件 SHA256
index.json           包名索引和可选 latest 版本表
data/<包名>.json      该包的合并后漏洞记录
```

`snapshot` 默认取生成机器当天日期，也可通过 `--snapshot` 指定。它是本地库的批次标识，不是上游数据完整性的证明；重新给旧数据设置今天的日期不会使其变新。下载时间、原始文件哈希和原始文件本身应一并保留。

源码依据：[同步器](../sync/sync.py)、[数据库读写与更新](../pythonscan/db.py)、[匹配引擎](../pythonscan/matching.py)。

## 外网机器准备条件

外网机器需要 Python 3.9 或以上版本，以及包含 `sync/` 和 `pythonscan/` 的项目源码。同步器使用标准库，正常运行无需安装额外 Python 包。仅安装扫描器或下载两个 EXE，不等于拥有同步器。

本节和后续外网命令在 **项目源码根目录** 的 PowerShell 中执行。确认入口可用：

```powershell
python --version
python -m sync.sync build --help
```

访问默认下载源需要网络能连接 `osv-vulnerabilities.storage.googleapis.com`。启用 `--fetch-latest` 时还需连接 `pypi.org`。扫描端无需执行这些联网操作。

外网保存以下目录：

```text
data/raw/      每批次的 OSV 原始 ZIP
data/full/     每批次的 PythonScan 全量库，供下一次增量作为基准
data/delta/    发往内网的增量包
data/audit/    文件哈希、构建输出、验证报告和操作记录
```

`data/` 已被 Git 忽略。这些资料需要另行归档，不能只依赖源码仓库保存。

## 首次准备全量库

### 下载并保留本次原始数据

日期使用外网机器本地日期；确认系统时间正确。以下变量名在本次准备过程中持续使用。

```powershell
# 确定本次批次，并创建归档目录。
$DbDate = Get-Date -Format 'yyyy-MM-dd'
$DbStamp = $DbDate.Replace('-', '')
New-Item -ItemType Directory -Force -Path .\data\raw, .\data\full, .\data\delta, .\data\audit | Out-Null
$RawDb = ".\data\raw\osv-PyPI-$DbStamp.zip"
$FullDb = ".\data\full\pypi-advisories-$DbStamp.zip"

# 下载一次；后续全量和增量构建均使用这个文件。
Invoke-WebRequest -Uri 'https://osv-vulnerabilities.storage.googleapis.com/PyPI/all.zip' -OutFile $RawDb -ErrorAction Stop
Get-FileHash -LiteralPath $RawDb -Algorithm SHA256 | Format-List | Out-File ".\data\audit\raw-$DbStamp.sha256.txt" -Encoding utf8
```

如果需要代理，在 `Invoke-WebRequest` 上添加实际代理地址，例如 `-Proxy 'http://127.0.0.1:7890'`。这个地址只是示例，必须替换为本机可用配置。

也可让同步器直接下载 URL，此时使用 `--proxy` 配置代理。这里采用显式下载以便保留原始数据，并保证本次全量和增量构建使用同一个源文件。

### 转换为 PythonScan 全量库

```powershell
python -m sync.sync build --src $RawDb --out $FullDb --snapshot $DbDate 2>&1 | Tee-Object -FilePath ".\data\audit\build-full-$DbStamp.log"
if ($LASTEXITCODE -ne 0) { throw '全量库构建失败，请检查构建日志。' }

python -m pythonscan db info --db $FullDb
if ($LASTEXITCODE -ne 0) { throw '无法读取生成的全量库。' }
Get-FileHash -LiteralPath $FullDb -Algorithm SHA256 | Format-List | Out-File ".\data\audit\full-$DbStamp.sha256.txt" -Encoding utf8
```

记录快照日期、记录数和包数，与上一批次或预期规模对照。无合理原因出现空库或明显下降时，检查下载结果和构建日志，再决定是否摆渡；ZIP 能打开或构建返回 0 不足以证明漏洞数据完整。

完成本节后，首次部署需要摆渡本次 `$FullDb`、对应 SHA256 记录和批次操作记录。原始 ZIP 留在外网归档，不需拿到内网执行。

## 后续每次准备与更新

### 先确定内网当前基准

内网维护人员先执行 `db info`，确认当前使用的库路径、快照和记录数，并将结果提供给外网维护人员。外网的上一份全量库应对应内网当前批次的数据；不要仅凭文件名猜测基准。

在外网重复“下载并保留本次原始数据”和“转换为 PythonScan 全量库”两节。**即使本次只摆渡增量包，也要保留本次生成的全量库作为下一次基准。** `--prev` 只接受全量库，不能把上一份增量包作为下一次基准。

若外网尚无历史基准，v0.1.0 的 `release/pypi-advisories-20260920.zip` 可作为首次基准，但内网必须正在使用对应的预置批次。若内网状态无法确认，直接准备并导入本次新全量库。

### 从同一原始数据生成增量包

以下示例假设内网基准日期为 `2026-09-20`，外网已把对应全量库保存在 `data/full/`。

```powershell
# 基准日期必须根据内网 db info 的实际结果填写。
$BaseDate = '2026-09-20'
$BaseStamp = $BaseDate.Replace('-', '')
$PrevDb = ".\data\full\pypi-advisories-$BaseStamp.zip"
$DeltaDb = ".\data\delta\delta-$BaseStamp-to-$DbStamp.zip"

python -m sync.sync build --src $RawDb --prev $PrevDb --out $DeltaDb --snapshot $DbDate 2>&1 | Tee-Object -FilePath ".\data\audit\build-delta-$DbStamp.log"
if ($LASTEXITCODE -ne 0) { throw '增量包构建失败，请检查基准库及日志。' }
Get-FileHash -LiteralPath $DeltaDb -Algorithm SHA256 | Format-List | Out-File ".\data\audit\delta-$DbStamp.sha256.txt" -Encoding utf8
```

增量包按包记录内容的哈希比较，包含新增或修改的包、删除的包，以及可选的最新版本变更。它不是“只抓取 OSV 新公告”：当前同步器仍读取最新的整份 PyPI 原始 ZIP。OSV 提供的 `modified_id.csv` 可用于发现上游近期变更，但本项目尚未实现该下载路径。[OSV 近期变更下载说明](https://google.github.io/osv.dev/data/#downloading-recent-changes)

程序衔接校验比较的是 `base` 与本地 `snapshot`，不会核对旧库全部内容。应保持基准数据和批次记录一致；当前按日期标识批次，避免同一日期发布多份内容不同、名称相同的增量链。

### 在外网先试应用增量

不要直接覆盖外网归档的上一版全量库。将它导入独立验证路径，再应用增量：

```powershell
$CheckDb = ".\data\audit\check-$DbStamp.zip"
python -m pythonscan db import $PrevDb --db $CheckDb
if ($LASTEXITCODE -ne 0) { throw '基准库验证导入失败。' }
python -m pythonscan db update $DeltaDb --db $CheckDb
if ($LASTEXITCODE -ne 0) { throw '增量包试应用失败，暂不摆渡。' }
python -m pythonscan db info --db $CheckDb
if ($LASTEXITCODE -ne 0) { throw '试应用后的库无法读取。' }
```

试应用后的快照、包记录内容和记录数应与本次全量库一致。合并过程会重写 manifest 和 ZIP，因此“试应用后的 ZIP”与“本次直接生成的全量 ZIP”不必具有相同的文件 SHA256；二者各自的哈希用于传输和归档核验。

常规摆渡本次增量包及校验记录。若增量链断档、基准不明确或试应用失败，改为摆渡本次新全量库。下一次仍使用本次归档的全量库作为基准，并以已实际导入内网的批次为准。

## 内网导入与核验

以下命令在 **Windows 发行包解压目录** 中执行。`pythonscan.exe` 位于该目录，不需要安装 Python。假设收到的 ZIP 和校验记录已放入该目录。

### 校验传输并备份旧库

```powershell
# 以实际收到的文件名为准；逐项与外网提供的 SHA256 比较。
Get-FileHash -LiteralPath .\pypi-advisories-20261014.zip -Algorithm SHA256

# 明确指定本次维护的库路径，避免操作到另一份库。
$LiveDb = Join-Path $env:USERPROFILE '.pythonscan\vulndb.zip'
New-Item -ItemType Directory -Force -Path .\db-backup | Out-Null
if (Test-Path -LiteralPath $LiveDb) {
    Copy-Item -LiteralPath $LiveDb -Destination (Join-Path .\db-backup ("vulndb-before-" + (Get-Date -Format 'yyyyMMdd-HHmmss') + '.zip'))
}
```

收到增量包时，校验该增量文件的 SHA256。更新前关闭正在使用目标库的 GUI 或扫描进程。SHA256 用于确认文件与外网记录一致；校验记录也应来自已确认的交付渠道。

### 选择全量导入或增量应用

以下两种操作根据实际交付文件选择一种，不要对同一目标库先导入本次全量、再应用同一目标日期的增量。

```powershell
# 首次部署、增量断档或准备重新建立基准时，导入全量库。
.\pythonscan.exe db import .\pypi-advisories-20261014.zip --db $LiveDb
if ($LASTEXITCODE -ne 0) { throw '全量库导入失败。' }
```

```powershell
# 当前库基准为 2026-09-20 时，应用发往 2026-10-14 的增量包。
.\pythonscan.exe db update .\delta-20260920-to-20261014.zip --db $LiveDb
if ($LASTEXITCODE -ne 0) { throw '增量库更新失败。' }
```

日期和文件名是示例，操作时替换为本批次实际值。全量导入会覆盖目标库；增量不衔接会拒绝应用，应补齐中间批次或导入最新全量库，不要手动修改 `base` 或 `snapshot` 来绕过检查。

### 查看状态并执行已知漏洞扫描

```powershell
.\pythonscan.exe db info --db $LiveDb
if ($LASTEXITCODE -ne 0) { throw '更新后的库无法读取。' }

'requests==2.28.0' | Set-Content -LiteralPath .\db-smoke-deps.txt -Encoding utf8
.\pythonscan.exe scan -i .\db-smoke-deps.txt --db $LiveDb --json .\db-smoke-result.json -o .\db-smoke-report.html
$ScanExit = $LASTEXITCODE
if ($ScanExit -notin @(0, 1)) { throw '扫描执行失败。' }
```

确认快照与交付批次一致，并检查 JSON 中是否检出 `CVE-2023-32681` 或其别名 `GHSA-j8r2-6x86-q33q`。这个已知漏洞样例预期返回 **1**，表示扫描完成且发现漏洞；0 表示未发现，2 表示执行错误。若该样例不再命中，应核对上游公告是否变化及库构建是否正常，不要仅依据退出码 0 判定更新有效。[该漏洞的 OSV 公告](https://osv.dev/vulnerability/GHSA-j8r2-6x86-q33q)

该样例验证库能加载和检索，不能代表全部记录正确。保留 `db info` 输出、JSON、HTML 和实际退出码。

GUI 用户更新后重新打开界面，并选择 `$LiveDb` 指向的库。直接选择新全量 ZIP 也能扫描，但 GUI 选中的库可能与 CLI 默认库不同；操作记录应写明实际路径。GUI 不能直接把增量 ZIP 当全量库选择。

### 回滚

发生异常时，先关闭使用目标库的程序，再将备份的旧全量库通过 `db import <备份文件> --db $LiveDb` 导回，检查快照并复扫。回滚后同步通知外网维护人员，后续增量必须以回滚后的实际批次为基准。

## 是否抓取最新包版本

常规流程默认省略 `--fetch-latest`，减少额外网络请求。需要在报告中显示库内最新版本时，替换本次全量构建命令，使用本批次新建的缓存：

```powershell
$LatestCache = ".\data\raw\latest-$DbStamp.json"
python -m sync.sync build --src $RawDb --out $FullDb --snapshot $DbDate --fetch-latest --latest-cache $LatestCache
if ($LASTEXITCODE -ne 0) { throw '带最新版本信息的全量库构建失败。' }
```

随后生成同一批次增量时，也添加 `--fetch-latest --latest-cache $LatestCache`，复用本轮抓取结果。抓取前确认此缓存没有被其他批次使用；当前实现对已缓存包不再请求 PyPI，长期复用旧缓存会导致最新版本信息不刷新。

曾启用最新版本表的库，后续应持续刷新该信息。当前增量更新不会自动清除所有未提供的旧 latest 条目；如果希望完全去掉旧表，导入本次未启用此参数的新全量库。

## 每批次交付与归档记录

| 项目 | 记录内容 |
| --- | --- |
| 批次与人员 | 快照标识、下载与生成时间及其时区、准备人员、内网导入人员 |
| 上游来源 | 下载 URL、原始 ZIP 文件名和 SHA256；可同时记录 HTTP Last-Modified、ETag |
| 生成程序 | PythonScan 版本、源码提交，可用 `git rev-parse HEAD` 获取 |
| 生成参数 | 完整构建命令、是否使用代理及 `--fetch-latest`；不记录代理口令 |
| 数据规模 | 包数、记录数、与前次的变化，以及增量新增修改和删除数 |
| 发布文件 | 新全量库、增量包及各自 SHA256；原始 ZIP 留外网 |
| 基准衔接 | 内网实际库路径、当前快照、所用外网基准全量库及批次 |
| 验证与恢复 | 构建输出、试应用结果、扫描报告、旧库备份路径、成功或失败记录 |

更新周期按团队摆渡计划安排，例如每周一批；重要项目上线前再准备一批。这是维护安排，不是 OSV 对本工具的更新承诺。默认 90 天过期提示只提醒库龄，不代替更新策略，也不证明库未过期时数据一定完整。

## 操作命令验证结果

2026-10-14 在 Windows 上使用两批小规模 OSV 格式测试记录，验证了本文的构建和维护命令。内网操作使用 v0.1.0 已发布的 `pythonscan.exe`，未更改或重新打包程序。

| 操作 | 验证结果 |
| --- | --- |
| 生成两批全量库 | 第一批 2 条记录，第二批 3 条记录；生成和读取均成功 |
| 从第一批生成发往第二批的增量 | 2 个包新增或修改、1 个包删除 |
| 用 EXE 导入原始 OSV ZIP | 返回 2，拒绝没有 PythonScan manifest 的原始数据 |
| 用 EXE 导入基准库并应用增量 | 均返回 0；合并后的包索引和包数据与第二批直接生成的全量库一致 |
| 用 EXE 扫描测试依赖并导出报告 | 返回 1，JSON 中包含测试公告的 CVE 别名，HTML 报告生成成功 |
| 通过导入备份回滚 | 返回 0，恢复第一批快照 |

这些结果验证操作流程和接口衔接；每次实际从上游下载的新数据，仍需执行本次构建、规模核对和扫描核验。

## 当前版本的数据处理边界

v0.1.0 已实现数据与程序分离，仍存在影响结果正确性的已知问题：

| 当前行为 | 对操作及结果解释的影响 |
| --- | --- |
| 同步器无条件删除 `affected.versions`，匹配器未完整处理版本列表与范围的并集 | 仅枚举受影响版本的记录可能漏报；下载新数据不能修复该逻辑 |
| 同步器未过滤并保留 `withdrawn` 撤回标记 | 已撤回公告可能继续出现在结果中 |
| 无法解析的范围或版本未完整传递“未知”状态，修复建议未重新验证目标 | “未发现漏洞”和建议版本仍需结合原公告核对 |
| `db import` 校验 manifest 中声明的文件哈希，扫描查询未验证包数据 SHA256 | 通过 GUI 或 `--db` 直接加载不等同于全量导入校验；交付时保留外部哈希并使用导入流程 |
| 同步器跳过无法解码或解析的 JSON，当前日志没有完整的跳过统计 | 需保留原始 ZIP，关注异常规模变化，不能只看构建退出码 |

OSV 规范要求用版本列表或范围判断受影响版本，并定义了撤回字段及范围事件。后续完善同步器和匹配器时应以该协议为依据。[OSV 格式与判定规范](https://ossf.github.io/osv-schema/)

因此，需要分别维护“漏洞数据更新”和“程序逻辑修复”：公告新增、修改通过更新库交付；字段处理、版本判断和建议算法问题通过程序版本修复。维护人员不应把库更新等同于修复所有漏报或误报。
